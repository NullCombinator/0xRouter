## Phase 2: Foundational (blocking)

**⚠️ CRITICAL**: no read moves before T006 is committed.

### The byte-for-byte gate (research R4)

- [X] T003 Write fixture-home builders in `crates/nullrouter-engine/src/testkit/homes.rs` (declared in `crates/nullrouter-engine/src/testkit/mod.rs`, behind the existing `testkit` feature), so the CLI's and the server's tests use the same homes. They write the home's files through the engine's and registry's own APIs (not by running the CLI), with a pinned clock and fixed ids. The homes cover:
  - every account kind and state (key, env-var key, signed-in, needs sign-in, disabled, cooling down);
  - unified models: one whose members differ in `context_length`, one dropped because its member's plugin was skipped;
  - bundled, installed and community plugins;
  - keys, including a revoked one and one with its own break behaviour;
  - quota history for one polled account;
  - records over several days, including in-flight, cut-short, `usage not reported`, and a request by a key that `keys.toml` names.
- [X] T004 Write `crates/nullrouter-cli/tests/read_golden.rs`. For each fixture home, it runs every listed read with and without `--json`, with the server stopped and running (`testkit` server):
  - `accounts list`, `accounts list --long`;
  - `quota`, `quota history <p> <n>`;
  - `routing`, `routing <target>`;
  - `records list` with each filter and `--limit`, `records show <id>` for an in-flight, a cut-short and a finished record;
  - `providers`, `providers --capability tts`, `model <p> <m>`;
  - `plugins list`, `plugins list --community`;
  - `keys list`, `check`;
  - `resolve <direct>`, `resolve <unified>`, `resolve <unknown>`.

  It compares stdout, stderr and the exit code with `tests/golden/<home>/<server state>/<command>.txt`. With `NR_BLESS=1` it writes the files instead. A field that cannot be pinned (a cooldown counted from the real clock in a running server) is masked by field name only, and the golden's header lists every mask.
  *Done with two deviations: cooling down lives only in the server's memory (`cooldown.rs`), so no fixture home holds it and no golden covers it; and a home with a polled account (`polled`) is stopped-only, since a running server would poll its provider. Unfinished records are appended after the server starts (it settles open ones at startup).*
- [X] T005 Run `NR_BLESS=1 cargo test -p nullrouter-cli -j 2 --test read_golden` on the unchanged code, then run it again without `NR_BLESS` and check it passes twice in a row (no flakiness)
- [X] T006 Commit the fixture builders, the suite and the goldens on their own: `test(008): golden outputs of every CLI read before the move`

### The read-model skeleton (contracts/read-model.md)

- [X] T007 In `crates/nullrouter-server/src/views/mod.rs`, define:
  - `View { json: serde_json::Value, extra: serde_json::Value }`;
  - `ViewError { message: String, code: u8 }`, carrying the CLI's exact message and exit code;
  - `Live { answers: BTreeMap<&'static str, Option<Value>>, running: bool }`, where `None` means "no server".
- [X] T008 In `crates/nullrouter-server/src/views/mod.rs`, add the two route helpers:
  - `fetch_socket(home, needs, args) -> Live` (the CLI route), which uses `operator::call` per op and treats a refused connection as "no server". It sets `running` by connecting to the socket, as today's `server_runs` in `crates/nullrouter-cli/src/cmd/records.rs` does, even when `needs` is empty;
  - `async fn fetch_in_process(engine, needs, args) -> Live` (the in-server route), which uses `operator::handle` with `running = true`.

  Each builds an op's request from the view's arguments (for example `routing.view` with `target`, `quota.list` with `provider`/`name`). Unit tests use a fake answer map.
- [X] T009 Add `async fn run_in_process<F>(engine, needs, args, build: F)` to `crates/nullrouter-server/src/views/mod.rs`. It fetches with `fetch_in_process`, then calls the sync `build` in `tokio::task::spawn_blocking` (constitution: no blocking I/O on the executor)

## Phase 4: User Story 2 — Page back through request records (Priority: P2)

**Goal**: `records list --before <ID>`, with the newest page read from the end of its segment.

**Independent Test**: `cargo test -p nullrouter-engine -j 2 --test records_page` passes;
`cargo bench -p nullrouter-engine --bench records_page` meets research R7.

### Tests for User Story 2

- [X] T026 [P] [US2] Write `crates/nullrouter-engine/tests/records_page.rs` (SC-005). On journals over several days and on one big day segment, it pages from the newest record with `limit` 1, 7 and 50, passing each page's last id as `before`. The pages joined must equal the full listing, with and without each filter, and with in-flight records. Also cover:
  - a fixture whose `open` lines are written out of id order by up to 59 s (research R6 margin);
  - a cursor on the last record of a day, and on the first record after midnight;
  - an unknown id (error), and a pruned id (error).
- [X] T027 [P] [US2] Write the Criterion bench `crates/nullrouter-engine/benches/records_page.rs` and register it in `crates/nullrouter-engine/Cargo.toml`. Cases:
  - the newest page of 50 on 1k records, on 100k over 30 daily segments, and on 100k in one segment;
  - a page 50,000 records back in both 100k layouts.

  Records are about 1 KB each, generated once into a temp home per case.

### Implementation for User Story 2

- [X] T028 [US2] Add `before: Option<String>` to `Filter` in `crates/nullrouter-engine/src/journal/records.rs`. Rule (data-model.md): "Only records whose id sorts below it. The id must name a record, else `no record <ID>` (exit 1). Combines with every other field."
- [X] T029 [US2] In `crates/nullrouter-engine/src/journal/records.rs`, add the cursor lookup. Decode the ULID's time, find that UTC day's segment and the day either side, and use the existing cheap `contains` test before folding. It returns whether the id names a record (research R6.2)
- [X] T030 [US2] In `crates/nullrouter-engine/src/journal/records.rs`, read a segment from its end in 16 KiB blocks, folding lines as they come. A record is complete once its `open` line is seen. Stop when `limit` complete matching records older than `before` are in hand **and** the oldest `open` line read is more than 60 s older, by ULID time, than the oldest record kept (research R6.3). Without a limit, read whole segments as today. `read` uses this path; the result order stays id descending
- [X] T031 [US2] Add `before` to the `records.list` op in `crates/nullrouter-server/src/operator.rs` (doc table at the top too); an unknown id answers `{"ok":false,"error":"no record rq_…"}` (contracts/cli.md)
- [X] T032 [US2] Add `--before <ID>` to `records list` in `crates/nullrouter-cli/src/cmd/records.rs` and pass it through `views::records`; an unknown id prints `no record <ID>` on stderr and exits 1
- [X] T033 [US2] Add `records list --before` cases to `crates/nullrouter-cli/tests/read_golden.rs` and bless only the new goldens in this commit
- [X] T034 [US2] Run the bench on this machine (`nice`, `-j 2`). Record the numbers against the targets of research R7 in `specs/008-read-model/bench-baseline.md`. If a target is missed, stop and report it; don't change the target

## Implementation Strategy

1. **MVP = Phase 1, Phase 2 and US1**: every read from one source, output unchanged, both routes
   tested. This is what the dashboard slice needs first.
2. Then US2 (paging), the largest risk after US1, with its bench gate.
3. Then US3 and US4, which are small.
4. Each story ends at a checkpoint where the goldens and the crate's tests are green. Each story
   can be committed and reviewed on its own.
